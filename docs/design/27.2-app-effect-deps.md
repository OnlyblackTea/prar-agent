# 27.2 App.tsx effect 依赖数组收敛（react-hooks/exhaustive-deps 三警告）

> 前置：27.1（构建产物卫生）收口时 `npm run lint` 报出 `src/App.tsx` 三条
> `react-hooks/exhaustive-deps` 警告。当时判定属独立缺陷，不塞进 27.1 的 commit。
> 本设计为独立修复任务，不属 ROADMAP 任何 milestone，编号沿用 15.1 / 24.1 / 27.1 的小数先例。
> 用户决策：A+B（27.1）一个 commit、C（24.1）一个 commit、D（本设计）一个 commit。

## 1. 背景与目标

`frontend/eslint.config.js` 走 flat config，`rules` 里展开
`...reactHooks.configs.recommended.rules`，其中 `react-hooks/exhaustive-deps` 为 **warn**。
`npm run lint`（= `eslint .`）当前实测输出（2026-09-04）：

```
F:\workspace\prar-agent\frontend\src\App.tsx
  135:6  warning  React Hook useEffect has missing dependencies: 'state.planVersion' and
                  'state.sessionId'. Either include them or remove the dependency array
  145:6  warning  React Hook useEffect has a missing dependency: 'state.sessionId'.
                  Either include it or remove the dependency array
  178:6  warning  React Hook useEffect has a missing dependency: 'state.comments'.
                  Either include it or remove the dependency array

✖ 3 problems (0 errors, 3 warnings)
```

三条警告分属两类，**必须分开处置**，不能一律"把缺的依赖加进去"：

### 1.1 真缺的依赖：`state.sessionId`（:135 / :145）

两个 effect 体内都读了 `state.sessionId`（`listComments(state.sessionId, …)` /
`listPlans(state.sessionId)`），但依赖数组里没有它。这是**依赖数组与 effect 体实际读取的值不一致**。

需要如实说明的是：**当前无可复现的症状**。UI 上没有"在 review 态直接切会话"的入口 ——
换会话必然经过 `createSession` → status 回到 `idle`/`streaming`，而 `state.status` 本就在依赖数组里，
effect 会因 status 变化而重跑。所以加 `state.sessionId` 是**防御性正确**，不是在修一个用户可见的 bug。
把它写清楚，避免 commit message 夸大成"修复了会话切换不刷新评论"。

### 1.2 有意为之的原始值代理：`reviewPlanVersion`（:135 / :145）与 `commentsLen`（:178）

这两处**不是漏写依赖，是刻意用稳定的原始值代替对象/数组 identity**，属于设计意图，
不能"按 lint 建议"改回去：

| 代理 | 定义 | 代替的真实值 | 为什么必须是代理 |
|---|---|---|---|
| `reviewPlanVersion` | `status ∈ {review, action_review} ? state.planVersion : 0`（:105-106） | `state.planVersion` | 流式/执行期间恒为 `0`。若直接依赖 `state.planVersion`，`streaming`/`acting` 期间的版本号变动会触发 effect 重跑（虽然体内按 status 早退，但那是白跑） |
| `commentsLen` | `status === 'review' ? state.comments.length : 0`（:150） | `state.comments` | 该 effect 会做**全文档 `descendants` 扫描 + `applyAnchorMark` 写 ProseMirror 文档 + `setDangling`**。用数组 identity 会让任何产出新 `comments` 数组的 dispatch（即使内容未变）都触发一轮全文档扫描与编辑器写入 |

`:178` 那处若真按 lint 建议加 `state.comments`，风险最高：effect 内 `setDangling(nextDangling)`
每次都 new 一个 `Set`，配合数组 identity 依赖会显著放大重放锚点的频次。
`existingAnchors` 幂等守卫能保证**结果**正确，但保证不了**开销**可接受。

### 1.3 为什么不能干脆删掉代理

`reviewPlanVersion` 与 `commentsLen` 经 grep 确认**只在依赖数组里被使用**（`:105/:135/:145`、`:150/:178`），
别处（JSX、其他 hook）没有引用。所以"从依赖数组里拿掉代理、改依赖真实值"必然让这两个变量变成未使用，
撞上 `tseslint.configs.recommended` 的 `@typescript-eslint/no-unused-vars`（**error** 级），
进而要删掉 `:105-106` 与 `:150` 两处定义 —— 那就是把 M2-13 / M2-14 的既定设计推翻重写，
属无关重构，且改变了 effect 的触发时机（需重新做全套 review UI 的 E2E 验证）。

**目标**：`npm run lint` 输出 **0 error / 0 warning**，且

- 三个 effect 的**触发时机逐条不变**（`:178` 尤其不能变成按数组 identity 触发）；
- `state.sessionId` 进入 `:135` / `:145` 的依赖数组，使依赖与 effect 体读取的值一致；
- 每处 `eslint-disable` 都带**具体理由**，而非裸关闭规则；
- 零新依赖、零产品行为变更、不动 `eslint.config.js`（不把规则全局降级或关闭）。

## 3. 接口设计

**无对外接口变更。** 全部改动落在 `App.tsx` 的三个 effect 的依赖数组与其上方注释。

### 3.1 逐处改法

| 行（改动前） | 依赖数组改为 | 附加 |
|---|---|---|
| `:135` | `[state.status, state.sessionId, reviewPlanVersion]` | 前置 `// eslint-disable-next-line react-hooks/exhaustive-deps -- …`，理由指向 `reviewPlanVersion` 代理 |
| `:145` | `[state.status, state.sessionId, reviewPlanVersion]` | 同上 |
| `:178` | `[state.status, commentsLen, viewingVersion]`（**不变**） | 前置 disable 注释，理由指向 `commentsLen` 代理 |

`:178` 的依赖数组一个元素都不动 —— 那里唯一的"缺失依赖" `state.comments` 正是被 `commentsLen`
有意替代的对象，加进去就等于推翻 §1.2 的设计。

### 3.2 disable 注释的写法约束

- 用 `eslint-disable-next-line`（**不用** `eslint-disable-line`）：警告报在依赖数组所在行
  （`135:6` 的列 6 就是 `[`），`-next-line` 放在该行之前可精确覆盖，且不会把注释和长依赖数组挤在同一行。
- 规则名必须写全 `react-hooks/exhaustive-deps`，**不得**用裸 `eslint-disable-next-line`（那会屏蔽该行所有规则）。
- 每条 disable 必须带 `--` 后的简短理由，并把完整论证放在 effect 上方的既有设计注释里
  （`:127` / `:137` / `:147-149` 已有注释，本次在其后补一句代理理由）。
  理由要写"为什么这个依赖是被代理的"，而不是"lint 报了所以关掉"。
- 三处合计新增 3 条 disable 注释。`src/` 下此前 `eslint-disable` 出现次数为 **0**（grep 实测），
  本次是首次引入，故必须在设计文档里留下判例：**只允许为"有意代理"这一类理由使用，
  不允许用于绕过真实缺陷**。

### 3.3 被否的候选方案

1. **按 lint 建议把 `state.planVersion` / `state.comments` 直接加进依赖数组** ——
   否。`:178` 会退化成按数组 identity 触发全文档扫描（§1.2）；`:135`/`:145` 会让 `reviewPlanVersion`
   变成冗余依赖，两个语义重叠的依赖并存反而更难读。
2. **删掉两个代理变量，改依赖真实值** —— 否。触发时机改变，属推翻 M2-13/M2-14 既定设计的无关重构（§1.3）。
3. **在 `eslint.config.js` 里把 `react-hooks/exhaustive-deps` 降为 `off` 或全局忽略 `App.tsx`** ——
   否。那会让**将来**真实的漏依赖缺陷也静默通过，用一个全局的失明换三处局部的安静。
4. **把三个 effect 抽成自定义 hook** —— 否。规则照样会在新 hook 里报同样的警告，只是把问题搬了个家，
   还额外引入本次不需要的抽象。

## 8. 设计变更 (2026-09-04)

编码阶段发现 §3.1 对 `:135` / `:145` 的处方（把 `state.sessionId` 加进依赖数组）**在本项目的类型系统下不可表达**，改为三个依赖数组全部保持原样。本节记录偏差、被否决的替代方案，以及一条把结论从"防御性正确"升级为"provably 冗余"的实测事实。

### 8.1 §3.1 处方撞上 TS2339

按 §3.1 原文实施后 `npm run typecheck` 立即报 2 个错：

```
src/App.tsx(138,27): error TS2339: Property 'sessionId' does not exist on type 'SessionState'.
  Property 'sessionId' does not exist on type '{ status: "idle"; }'.
src/App.tsx(149,27): error TS2339: Property 'sessionId' does not exist on type 'SessionState'.
  Property 'sessionId' does not exist on type '{ status: "idle"; }'.
```

根因：`SessionState`（`src/state/sessionReducer.ts:29-37`）是 discriminated union，8 个分支里
`{ status: 'idle' }` 与 `{ status: 'error'; code; message }` **没有 `sessionId` 属性**。
effect 体内读 `state.sessionId` 之所以合法，是因为前面的 `if (state.status !== 'review' ...) return`
完成了窄化；而**依赖数组位于组件体作用域，没有任何窄化**，所以同一个表达式在那里不合法。

§3.1 只看了 lint 输出，没有核对 `SessionState` 的形状 —— 这是设计阶段的疏漏，不是实施阶段的偏差。

### 8.2 考察过的三个替代方案，及否决理由

| 方案 | 做法 | 否决理由 |
|---|---|---|
| a | 组件级派生 `const activeSessionId = state.status !== 'idle' && state.status !== 'error' ? state.sessionId : ''`，依赖数组放 `activeSessionId` | `exhaustive-deps` 按**语法**比对成员表达式：体内读的是 `state.sessionId`，依赖里是 `activeSessionId`，警告**照旧不消**（与 `reviewPlanVersion` 消不掉 `state.planVersion` 警告同理）。净结果是"多一个变量 + 仍需 disable"，严格劣于现状 |
| a′ | 在 a 的基础上把 effect 体内也改读 `activeSessionId` | 能消掉 `:145` 的警告，但在**已窄化**的 `review` 分支里，把"由类型系统保证等于当前会话"的 `state.sessionId` 换成一个普通 `string`，削弱了 union 的保障：将来谁改坏派生式，effect 会静默拉错会话。为一个无症状的收益引入真实回归面 |
| b | 依赖数组内联三元 `state.status !== 'idle' && state.status !== 'error' ? state.sessionId : ''` | 技术上可行（`state.sessionId` 字面出现在依赖数组里，警告会消），但两处重复的长三元塞进依赖数组，可读性差，且付出的复杂度同 a′ 一样只换来 §1.1 已认定无症状的收益 |

**选定方案：三个依赖数组全部保持 HEAD 原样**，三条警告统一用带理由的 `eslint-disable-next-line` 处置，
把 `state.sessionId` 从 §1.1 的"真缺依赖"重新归类到 §1.2 的"有意省略"。

### 8.3 决定性事实：`sessionId` 不可能在 status 不变时改变（实测核验）

§1.1 原先的措辞是"当前无可复现的症状 …… 属防御性正确"。实施阶段用
`grep -n "sessionId" src/state/sessionReducer.ts` 核验后，可以给出更强的结论：

- 全文件 8 处 `sessionId` 赋值中，只有 `:77` 取自 `action.sessionId`，而那一处属 `START_SESSION`
  分支，**同时**把 status 置为 `connecting`；
- 其余 7 处（`:85` / `:106` / `:143` / `:153` / `:244` / `:258` / `:272`）全是 `sessionId: state.sessionId`，原样继承。

所以在当前 reducer 下，**`sessionId` 的任何变化必然伴随 status 变化**，而 `state.status` 本就在三个依赖数组里。
加 `state.sessionId` 不是"防御性正确"，而是 **provably 冗余**。省略它没有留下任何已知缺口。

连带修正 §7 风险表第 2 行："加 `state.sessionId` 后触发时机变化导致重复请求"这一风险**不存在**，
因为最终没有加。该行保留原文不改，以记录设计阶段的判断过程。

### 8.4 净结果：本次改动是纯注释

三个依赖数组与 HEAD 逐字节相同，`git diff HEAD -- frontend/src/App.tsx` 只有注释行
（+11 / -2，全是 `//`）。因此 §2 的不变量"三个 effect 的触发时机不变"不是"验证后成立"，
而是**结构上不可能变**——运行时读到的依赖数组没有任何字节差异。

### 8.5 过程中撞到的 `Unused eslint-disable directive`

第一版实施按 §3.1 给 `:145` 也复制了一条 disable，lint 立刻报：

```
148:5  warning  Unused eslint-disable directive (no problems were reported from 'react-hooks/exhaustive-deps')
```

原因：`:145` 那个 effect 体内**只读 `state.sessionId`，不读 `state.planVersion`**（`:135` 那个才两者都读），
所以补上 sessionId 后它的警告全消，disable 变多余。`reportUnusedDisableDirectives` 生效，
说明 **disable 注释不能凭猜复制粘贴，每一条都必须由实际警告支撑**。这条护栏对后续新增 disable 同样适用。
