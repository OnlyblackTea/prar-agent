# 24.1 Consolidator 服务层测试的共享库隔离

> 前置：M4-24 收口后 `test_consolidator_service.py` 在共享 VM 库上会因**别人留下的行**而假失败。
> 本设计为独立修复任务，不属 ROADMAP 任何 milestone，编号沿用 15.1 / 27.1 的小数先例。
> 用户决策：与 27.1（构建产物卫生）、27.2（App.tsx effect 依赖）分别独立成 commit。

## 1. 背景与目标

`backend/tests/test_consolidator_service.py` 是**真 DB 集成测试**（`db` fixture 直连
`get_settings().database_url` → VM `192.168.1.147:5432/prar_agent`），靠
"只 flush 不 commit + teardown rollback" 做隔离。

该隔离只能保证**自己写的行**不残留，**挡不住共享库里别人已 commit 的行**。
而 Consolidator 依赖的三个查询全是**全表扫描**：

| 产品代码 | 语义 | 受污染的结果字段 |
|---|---|---|
| `memory_service.py:147-152` `list_unconsolidated` | `WHERE kind='episodic' AND consolidated_at IS NULL ORDER BY created_at LIMIT 20` | `result.processed = len(batch)` |
| `memory_service.py:181-186` `decay_importance` | `UPDATE ... WHERE kind IN ('semantic','procedural')`，返回 `rowcount` | `result.decayed` |
| 测试自己 `test_consolidator_service.py:241-246` | `SELECT count(*) WHERE kind='semantic'` | C4 的 `count == 1` |

已实测到的真实故障（2026-09-04，M4-24 收口期间）：VM 库里一行 E2E 残留 episodic
`8228bcd4-31d8-45fc-99d0-e744c2953b56` 令 **3 个用例假失败**，当时靠删掉那一行绕过。

**当前状态（本次实测）**：`memories` 表已空 —— 残留行已删，故 6 个用例现在全绿：

```
$ uv run pytest tests/test_consolidator_service.py -q
......                                                                   [100%]
6 passed in 0.74s
```

即缺陷是**潜伏的**：任何一次真实会话/E2E 冒烟写入 episodic 后未消费，下次跑测试就复发。
本次要修的是**复发条件**，不是当前症状。

## 3. 接口设计

**无产品代码接口变更。** 全部改动落在测试文件内。

### 3.1 为什么不改产品代码

三个候选方案被否：

1. 给 `list_unconsolidated` 加 `session_id` / `ids` 之类的 scope 参数 ——
   Consolidator 的**设计意图就是跨会话全局提炼**（提示词里的"跨会话知识"），
   加 scope 参数纯属为测试便利扩产品 API，违反"不写将来可能用到的扩展点"。
   且会牵动 `test_consolidator.py` 里 10 处 `AsyncMock(return_value=...)` 的单测。
2. 把 `processed` / `decayed` 改成只统计本用例创建的行 —— 要引入行来源追踪，
   产品复杂度上升，且改变了 `ConsolidateResult` 的既有语义（`/consolidate` 端点对外暴露它）。
3. 改用 testcontainers / 独立测试库 —— 引入新依赖与新基建，超出本次修复范围。

**采用**：沿用本文件既有的 `_clear_defaults` 手法（`:87-93`，
docstring 写的就是"VM DB 可能残留真实默认 adapter，测试事务内先清空保证确定性（rollback 复原）"）——
**在测试事务内把世界变成已知状态**，teardown rollback 复原，共享库零持久影响。

### 3.2 新增 `_isolate` helper

```python
class _Baseline(NamedTuple):
    decayable: int


async def _isolate(db: AsyncSession) -> _Baseline:
    """中和共享 VM 库残留行，令全表扫描型断言确定化（事务内执行，teardown rollback 复原）。

    与 _clear_defaults 同一手法。必须在 _seed_memory 之前调用，否则会消费掉本用例自己的原料。
    """
    await db.execute(
        update(models.Memory)
        .where(
            models.Memory.kind == "episodic",
            models.Memory.consolidated_at.is_(None),
        )
        .values(consolidated_at=func.now())
    )
    decayable = (
        await db.execute(
            select(func.count())
            .select_from(models.Memory)
            .where(models.Memory.kind.in_(("semantic", "procedural")))
        )
    ).scalar_one()
    return _Baseline(decayable=int(decayable))
```

两件事，分别对应两类污染：

- **残留 pending episodic → 标记为已消费**（UPDATE，非 DELETE）。
  这同时修掉 `processed` 膨胀**和** batch 挤占（`:176` 的边界脆弱）。
  选 UPDATE 而非 DELETE：与 `mark_consolidated` 的产品语义一致，破坏性最小。
- **残留 semantic/procedural → 只计数，不删不改**，作为基线返回。
  `decay_importance` 是全表 UPDATE，其 `rowcount` 必然包含残留行，
  无法在不删数据的前提下让它变小 —— 那就把断言从"绝对值"改成"基线 + 本用例增量"，
  既保持精确又不削弱覆盖。

### 3.3 断言改写

| 行 | 现状 | 改为 |
|---|---|---|
| `:198` | `assert second.decayed == 1` | `assert second.decayed == base.decayable + 1` |
| `:219` | `assert result.decayed == 2` | `assert result.decayed == base.decayable + 2` |
| `:241-246` | 全局 `count(*) WHERE kind='semantic' == 1` | id 集合差分：run 前后 semantic id 集合相等（合并走 UPDATE 覆盖，不新增行） |

`processed` 四处断言（`:157/:189/:194/:220`）**逐字不动** —— `_isolate` 已让它们的前提成立。

C4 的 id 集合差分需要一个 helper：

```python
async def _semantic_ids(db: AsyncSession) -> set[UUID]:
    rows = await db.execute(
        select(models.Memory.id).where(models.Memory.kind == "semantic")
    )
    return set(rows.scalars().all())
```

改写后 C4 的断言强度**高于**原来：原 `count == 1` 只证明"全局恰好一行 semantic"
（在共享库里这本来就是错的命题），新断言证明"合并未新增行"，
再叠加 `:247-250` 已有的 `existing.content` / `importance == 0.81`（证明合并命中的是本用例那行），
合起来精确表达了 C4 的意图。

### 3.4 调用点

`_isolate` 必须在 `_seed_memory` **之前**调用（否则会把本用例刚种的 episodic 原料一并消费掉）。
`_seed_adapter` 不碰 `memories` 表，顺序无关。

| 用例 | 是否加 `_isolate` | 理由 |
|---|---|---|
| C1 `test_distill_inserts_and_marks_batch` | 是 | `processed == 3` |
| C2 `test_second_run_no_llm_and_no_new_rows` | 是 | `processed` ×2 + `decayed` |
| C3 `test_decay_factor_floor_and_episodic_untouched` | 是 | `processed` + `decayed` |
| C4 `test_merge_when_identical_vector` | 是 | semantic id 差分需要已知基线 |
| C5 `test_no_default_adapter_raises` | **否** | 无计数断言；自行种 1 行 episodic 保证 batch 非空以触发 raise，残留行只会让 batch 更非空，结论不变 |
| C6 `test_llm_error_keeps_batch_unconsumed` | 是 | 断言本身不会假失败，但残留 ≥ 20 行会把本用例的 `row` 挤出 batch，令"LLM 失败前未标记"变成**空断言**（row 压根没被选中）。加 `_isolate` 才能保证用例真的在测它声称的东西 |

## 7. 风险与未决

| 风险 | 评估 | 处置 |
|---|---|---|
| `_isolate` 的 UPDATE 在共享库上取行锁，与真实运行的 consolidator 后台循环争用 | 低。锁只在测试事务存活期间持有（秒级）；且跑 pytest 时通常没起 uvicorn。既有 `_clear_defaults` 对 `model_adapters` 做的是同一件事，已是本文件接受的代价。 | 不处置。若将来出现阻塞，改为在 CI 里指向独立测试库（本设计 §3.1 方案 3），届时另开设计。 |
| `decayable` 基线假设 `decay_importance` 的 `rowcount` == 匹配行数 | 中。PostgreSQL 的 UPDATE 对每个匹配行都写新元组（即使新值等于旧值，如已在 floor 的行），故 `rowcount` == 匹配总数，与"值是否真变了"无关。 | 以 V2/V3 实测为准。若某方言下 `rowcount` 语义不同，退路是把 `:198`/`:219` 放宽为 `>=`（真实契约由 `:216-218` 的行级 importance 断言承载，不丢覆盖）。 |
| `_isolate` 忘记放在 `_seed_memory` 之前 | 中。放错会消费掉本用例自己的原料，导致 `processed == 0` 而不是膨胀 —— 症状明显，不会静默。 | 在 `_isolate` docstring 里写明调用时序约束；V2 会立刻抓到。 |
| 新增回归用例本身是否会污染共享库 | 否。所有写入都在 `db` fixture 的事务内，teardown `rollback`。 | 以 V8 实测确认。 |
| 是否顺手把 C4 的 `inserted/merged` 与 C1 的 `:172` 也改成 id 差分 | —— | **不改**。§1 清单已逐条论证它们可证明安全（相同 content → 距离 0 必排第一；`VALID_KINDS` 封闭）。改了属无关重构。 |

### 8.2 新增 `_pending_episodic_ids` helper（§3.2/§3.3 未列）

§5 步骤 6 要求 C7 断言"pending episodic 归零"。原打算在 C7 里就地
`store = MemoryService(db, emb)` 调产品的 `list_unconsolidated`，实测**新增 1 条
`arg-type` 错误**（`_FakeEmbedding` 不是 `EmbeddingService`），把总数推到 21，违反 §8.1 的净增 0。

故新增 helper，把该产品查询收进一处并显式 `type: ignore`：

```python
async def _pending_episodic_ids(db: AsyncSession, emb: _FakeEmbedding) -> set[UUID]:
    """走产品的 list_unconsolidated —— 断言真批次入口，而非本文件抄一份等价 SQL。"""
    # 伪嵌入替身不是 EmbeddingService 子类；同 _run 里对 router 的处理方式
    store = MemoryService(db, emb)  # type: ignore[arg-type]
    return {m.id for m in await store.list_unconsolidated(limit=20)}
```

保留"走产品查询"而非本文件抄一份等价 SQL：抄 SQL 测的是自己的副本，
`list_unconsolidated` 的 `WHERE`/`ORDER BY`/`LIMIT` 一旦改动，抄本不会跟着失败 ——
那就失去了 C7 的意义。

**已知不一致**：本文件另有 4 处 `MemoryService(db, emb)` / `Consolidator(embedding=emb)`
（`_seed_memory`、`_run`、C5、C6）**没有** `type: ignore`，正是基线 8 条的来源。
本次**不给它们补 ignore** —— 那属无关重构，且会把"净增 0"变成"净减 8"，
超出一个测试隔离修复的范围。

### 8.3 V3 抗残留手法加强：临时 autouse fixture 注入全部 7 个用例

§5 步骤 8 原写"临时把注入加到 C1/C2/C3/C4 顶部"。实际改用**临时 autouse fixture**，
在**全部 7 个**用例的测试体之前种入 3 行未消费 episodic + 1 行 semantic + 1 行 procedural：

- 覆盖面更大（C5/C6/C7 也吃到残留），且只需一处插入/一处删除，不易漏改。
- 额外收益：**实证确认了 §1 清单里判定为"可证明安全"的两条断言确实安全** ——
  C1 `:172` 的 `{m.kind for m in new_rows} == {"semantic","procedural"}` 在残留 semantic +
  procedural 同时存在时仍成立；C4 的 `inserted == 0 / merged == 1` 在残留 semantic 存在时
  仍命中本用例那行（相同 content → 余弦距离 0 必排第一）。原判定是推理，现在是实测。
- 该 fixture 验完已删除，`grep -n "TEMP-" tests/test_consolidator_service.py` 无输出。
